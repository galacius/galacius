Two rapid, unawaited calls from the frontend to the same Wails-bound Go method (e.g. two `mutate()` calls fired back-to-back from `useMutation`) can arrive at the Go method **in either order** — the IPC bridge does not preserve call order. If the Go method just overwrites shared state on every call (`a.activeNamespaces = namespaces`), whichever call happens to arrive last wins, even if it was actually the user's *earlier*, now-stale selection. This silently reverts a newer choice to an older one.

**Why:** Found via `superpowers:systematic-debugging` while investigating a live bug where rapidly toggling the namespace filter (twice within ~200ms) could leave the Helm Releases view (and every other namespace-scoped view) stuck showing data for the first click instead of the second. Confirmed via direct evidence: calling `window.go.app.App.SetActiveNamespaces(["default"])` then immediately `(["kube-system"])` with `Promise.all` — 40/40 trials showed Go could execute the calls in either order.

A Go-side sequence counter (e.g. the existing `logSeqs` pattern in `internal/app/logs.go`, which guards a stale background goroutine from outliving a newer one) does **not** work here, because the reordering happens *before* the Go method body starts executing (at the IPC dispatch layer) — by the time Go assigns a counter, the arrival order is already scrambled. The counter must be generated **frontend-side, synchronously, before the async IPC call goes out** (i.e., inside the `mutationFn`, not in a `useEffect` or after an `await`), then passed as an extra parameter so the Go side can drop any call whose `seq` is not strictly greater than the highest `seq` already applied.

Fixed in `internal/app/namespace.go` (`App.SetActiveNamespaces(namespaces []string, seq int64)`, backed by `App.activeNamespacesSeq` guarded by `a.mu`) and `frontend/src/app/clusters/modules/base/namespaces/hooks/data-mutation/useSetActiveNamespaces.tsx` (module-scoped `callSeq` counter incremented in `mutationFn`, before the call to `SetActiveNamespaces`).

**How to apply:** Any other Wails-bound method that (a) can plausibly be called twice in quick succession from the same UI interaction pattern (rapid toggles, fast typing with debounce disabled, etc.) and (b) just overwrites shared backend state rather than being naturally idempotent/commutative, is exposed to this same class of bug. When adding one, either debounce/cancel-and-replace on the frontend (e.g. abort the in-flight mutation before firing a new one) or apply this same frontend-generated-seq pattern. Don't reach for a Go-side-only sequence counter for this — it doesn't fix the actual race.

**Second occurrence — `App.Connect` (cluster-context switching), fixed 2026-08-27:** Rapid back-and-forth cluster switching (click A → B → A → B without waiting) could leave the backend's `activeContext` silently stuck on a stale cluster while the UI showed a different one — every `List*`/`Get*` call and the namespace filter would then keep serving the wrong cluster's data with no visible error. Root cause was the same class of bug as above but on `Connect`, which had *no* ordering guard at all: each `Connect(contextName)` call does slow, unlocked network work (build clientset, `Ping`, `NewFactoryHandle`'s up-to-30s informer sync) before acquiring `a.mu` and unconditionally doing `a.activeContext = contextName`. Two concurrent `Connect` calls for different contexts can therefore finish that slow work — and hit the write — in whichever order their respective clusters happen to respond, not the order the user clicked them in; whichever finishes last simply overwrites `activeContext`, even if it's the older, already-abandoned selection. (Notably, the frontend already had a `connectAttemptRef` monotonic counter in `App.tsx` guarding its *own* UI state against exactly this kind of stale completion — but that counter was never passed down to the Go `Connect` call, so the backend's `activeContext` had no equivalent protection.)

Fixed the same way as `SetActiveNamespaces`: added `App.activeContextSeq` (guarded by `a.mu`) and a `App.tryClaimConnectSeq(seq int64) bool` helper (`internal/app/utils.go`, next to `isActive`). `Connect(contextName string, seq int64)` now claims `seq` at entry (bailing out immediately, before any client/informer work, if a newer call already claimed a higher seq) and re-checks `seq < a.activeContextSeq` right before committing (`a.factories[contextName] = h; a.activeContext = contextName`) — if superseded by then, it stops the just-synced `kube.FactoryHandle` (`h.Stop()`) instead of leaking it and returns without touching shared state. Frontend: `useConnect.ts` grew its own module-scoped `callSeq` counter (mirroring `useSetActiveNamespaces.tsx`), incremented in `mutationFn` before calling `Connect`. `frontend/wailsjs/go/app/App.{js,d.ts}` were hand-edited to add the second `seq` param (not regenerated via `wails generate`, per the hand-maintained-bindings note in CLAUDE.md).

**How to apply (updated):** When adding a new Wails-bound method that transitions shared "which X is active" state (not just simple field overwrites like the namespace filter), check whether the transition itself involves slow/unlocked work before the commit point — if so, the same two-checkpoint pattern (claim-at-entry + re-verify-at-commit) is needed, not just a single seq check at the top like `SetActiveNamespaces` uses. A frontend-side attempt counter that only guards local UI state (like `connectAttemptRef` here) does *not* protect backend shared state unless that same counter is also threaded through to the Go call.

**Gotcha — seed frontend counters from `Date.now()`, not `0` (fixed 2026-09-11):** Ctrl+R (or any FE-only reload) reloads the webview's JS but not the long-lived Go backend process, so a module-scoped `callSeq` counter that starts at `0` resets across reload while the backend's corresponding seq (`activeContextSeq`, `activeNamespacesSeq`, etc.) keeps whatever value it had already claimed. Every post-reload call then carries a `seq` at or below the backend's high-water mark and gets silently dropped by the claim check — e.g. `useConnect.ts`'s `callSeq` resetting to `0` after reload left `App.Connect` stuck rejecting every call, so the backend's active context stayed on the pre-reload cluster while the frontend optimistically switched its UI, showing the old cluster's data under the new cluster's chrome. Fix: seed the counter from `let callSeq = Date.now()` instead of `0` — strictly increases across reloads (wall-clock time only goes up) and still strictly increases within a session via the existing `++`. Apply this to any new frontend-generated seq counter under this pattern, not just `useConnect.ts`.
